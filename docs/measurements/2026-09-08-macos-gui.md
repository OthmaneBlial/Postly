# Native GUI baseline — 8 September 2026

Five completed launches of the real Postly desktop app on a generated
10,000-request workspace. Host: `Mac14,2`, macOS 26.6 (25G72), native window
1280 × 713 points, captures 2560 × 1426 pixels. The final run ended at
`2026-09-07T22:36:24Z` (8 September, 00:36 in Paris).

## Results and what they mean

| Observation | Median ms | Min–max ms |
| --- | ---: | ---: |
| New process → visible WindowServer registration | 1,576.87 | 1,514.13–1,757.40 |
| New process → usable content observed in capture | 1,795.66 | 1,738.63–1,926.54 |
| Query `09999` → unique result observed | 805.80 | 803.44–829.44 |
| Select result → matching editor URL observed | 1,270.03 | 1,260.52–1,278.29 |
| Query `request` → 10,000 results observed | 1,310.46 | 1,302.23–1,313.33 |
| Large wheel event → last result observed | 769.26 | 755.16–771.53 |

Except for WindowServer registration, these are **upper bounds observed by a
capture**, not exact first-paint or event-processing durations. The clock is read
after capture completes; OCR then checks the pixels. An unsuccessful poll incurs
capture/OCR cost plus a 100 ms delay before retrying. Registration polling uses
10 ms intervals. Thus capture, polling and scheduling overhead is part of the
reported bound; do not describe these values as frame times.

Idle RSS: median **234,992 KiB (229.48 MiB)** over 15 samples, range
234,912–235,040 KiB. Three samples per process were read with `ps` roughly
5, 6 and 7 seconds after initial content recognition. This is the native app's
resident memory with 10,000 loaded requests, not the observer's memory, an empty
workspace baseline, peak allocation, GPU usage or a leak test.

Every final sample is retained. Processes were new for each sample, but filesystem
caches and private workspace UI state were **not** reset. Earlier protocol pilots
had warmed the machine; failed/earlier pilots were not pooled into the final
five-run data. No compiler/build job overlapped this final batch. Ordinary
desktop processes and the maintainer's original idle Postly instance stayed
running. This is a local baseline, not a controlled competitor comparison or a
cold-launch guarantee for other machines.

## Visible evidence

The CLI validator counted 10,000 requests; an independent check found 10,000
distinct IDs. The native UI showed the
unique `Last request` search result; opening it changed the editor URL to
`http://127.0.0.1:1/request/09999` and cleared search. A subsequent broad query
showed 10,000 matches, and a scroll event reached `Request 09998` and `Last request`.
The first final-run frames were inspected and retained without editing:

- [10,000 matching requests](../screenshots/postly-10000-search.png)
- [Bottom of the result list](../screenshots/postly-10000-scroll.png)

The observer uses one Unicode text event per query and a large synthetic pixel
wheel event. This checks end-to-end state transitions, **not** per-keystroke
responsiveness, continuous scrolling FPS, all keyboard navigation or all window
sizes. Code inspection still shows synchronous file reads during search and
construction of off-screen rows; investigate these before claiming a smooth
large-workspace experience.

## Validation and remaining gates

Swift compilation and strict `swift-format` lint passed. Five of five final runs
completed all checks. Both executable hashes match the raw report; only the
probe-created child processes ended, and the original user app remained alive.
The earlier locked-session failure was resolved by the session becoming unlocked,
not by bypassing macOS access controls. An OCR whitespace mismatch in a pilot
was corrected before the final batch. Raw captures/logs remain under the ignored
`tmp/gui-benchmark-2026-09-08/protected-five/` directory.

This supplies the first native startup/idle-memory/large-navigation observations
requested in the roadmap. It does not publish a new binary, prove an independent
installation, qualify Windows/Linux/Intel builds or replace external usability
and adoption evidence.
